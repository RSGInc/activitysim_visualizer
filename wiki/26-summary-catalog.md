# 26 - Summary Catalog

This page is the data dictionary for summary CSV tables from the Output
Processor. It explains what one row represents, how each table is used, and
what each output field means. The unified reference combines that analytical
context with the authoritative file names, schemas, builders, and input requirements.

## How to Interpret the Tables

- Weighting follows the analysis unit named in each field. Unless a table says
  otherwise, weighted people sum `per.finalweight`, weighted households sum
  `hh.finalweight`, weighted tours sum `tours.finalweight`, weighted trips sum
  `trips.finalweight`, and weighted vehicles sum `vehicles.finalweight`.
- A lower-level table can inherit its weight from a person or household, but
  its unit does not change. One person with weight `3.0` and four trip rows
  contributes `3.0` weighted persons and `12.0` weighted trips.
- In an unweighted cache, existing `finalweight` columns are set to `1.0`.
  Builder-specific participant and occupancy adjustments still apply. Measures
  read from assignment tables or externally supplied contracts are not
  automatically reweighted.
- Joint-tour participant expansion uses prepared `NUMBER_HH`, derived from the
  participant table when a tour has participant records, then from
  `number_of_participants`. An existing `NUMBER_HH` is retained as a final
  source before defaulting to one.
- Rates, percentages, averages, standard deviations, medians, percentiles, and
  fields with names such as `geography_count` use the calculation stated in
  their table entry; they do not share one universal weighting rule.
- Values such as `all_geographies`, `all_person_types`, `all_tour_purposes`,
  `all_tour_modes`, `All Modes`, `All Auto`, and `Daily` are rollups. Use either
  the rollup or its component rows, but do not add them together.
- `geography_type` names the configured spatial system, such as MAZ, TAZ,
  county, MPO, or a custom geography. `geography_id` is the identifier in that
  system. Each table description identifies the home, work, school,
  destination, or parking geography.
- Distance values use the units of the prepared distance or skim fields,
  usually miles. Distance histograms use `0` only for exact zero, `>0-<1` for
  positive sub-mile values, and whole-mile lower-bound labels thereafter.
  Missing, nonfinite, and negative distances are excluded. End bins such as
  `40+`, `20+`, or `51+` include all larger values.
- `time_bin` is the prepared ActivitySim period index: 1--24 for hourly inputs
  or 1--48 for half-hour-period inputs. Named `time_period` and `count_period`
  values come from configured or supplied period labels.
- Category codes and labels come from prepared ActivitySim values and the
  configured category mappings. Keep the code field for joins. Use the label
  field for presentation.
- A valid calculation can produce an empty CSV. That is distinct from a summary
  marked unavailable because an input table or field was absent. Use the
  summary manifest to identify the status.

## Build Status

The standard summarize workflow builds **85** tables. Of the **15** tables with
`Default build = no`, two are optional skim ECDF products and 13 are validation
contracts supplied by an external process through `summary_table_map`. The
visualizer does not calculate those contracts from `RunData`. The unified
reference below describes all 100 contracts.

## Unified Summary Reference

Each row combines the user-facing data dictionary with developer details from the
runtime registry. Category, analytical-use, and field-description text is maintained
in [`scripts/summary_catalog_metadata.yaml`](../scripts/summary_catalog_metadata.yaml);
file names, data types, build defaults, builders, and input requirements come from
the registered summary declarations.

A few categories have additional conventions:

- Skimjoin diagnostics use `skim_scenario` for the selected mode or a hypothetical
  sidecar mode. `all_records` identifies hypothetical values for all applicable
  records, and each table also includes an all-modes group.
- Processor-built validation summaries that use optional assignment tables are valid
  but empty when those inputs are absent.
- The 13 externally supplied validation contracts are registered for external CSV
  input. Their builders do not calculate values, so the supplying workflow is
  responsible for consistent units, period definitions, and values.

Regenerate the table after changing summary metadata or declarations:

```bash
uv run python scripts/generate_wiki_catalogs.py
```
